# 第一版 Demo 验收方案

## 1. 验收目标

第一版 Demo 验证 PfinderWithAI 能否在一个可控的简单微服务链路中，将用户提供的错误描述转化为可追溯的根因判断或下一步调查建议。

验收重点是打通一条完整的纵向链路，而不是覆盖所有故障类型或建设通用调用图平台。目标调用关系为 `A -> B -> C/D`，运行时可以接入公司内部真实 API，测试和仓库内示例必须使用合成或彻底匿名化的数据。

## 2. 前置条件

开始端到端验收前，需要具备以下只读能力：

- 根据系统、业务 Key、时间范围或 TraceID 查询日志。
- 通过 Pfinder 查询候选 Trace、Span 上下游关系、耗时、状态和异常摘要。
- 根据系统名称解析 Git 仓库地址、故障时对应的代码版本、日志实例、运行环境和 Pfinder 服务标识。
- 将目标版本克隆到隔离的临时只读工作区，并允许 Codex CodeInvestigator 在限定范围内进行静态调查。
- 提供一个可用的 LLMProvider 实现，用于主流程中的语义提取、歧义分析和假设验证。
- 运行环境已经为 Demo 身份配置必要的数据源和代码仓库只读权限。
- 将调查状态和过程写入 Demo 使用的 InvestigationStore。
- 提供可执行的 CLI 作为唯一交互入口，不依赖 HTTP 服务或前端页面。

公司内部 API 的具体协议、权限申请方式、限流规则和返回结构在接口能力整理完成后补充，不在本文中虚构。

## 3. 主验收场景

### 3.1 输入

用户提供以下信息，但不直接提供 TraceID：

- 错误现象或业务问题描述。
- 业务 Key，例如订单号或业务 ID。
- 起始系统。
- 大致发生时间或可接受的查询时间范围。

### 3.2 调查流程

1. ClueExtractor 从用户描述中提取现象、业务 Key、起始系统和时间范围，并标记缺失项与不确定项。
2. ContextResolver 通过内部元数据 Provider 补全 Git 仓库地址、目标版本、日志实例、运行环境和 Pfinder 服务标识。
3. 主调查 Agent 查询起始系统日志，从业务 Key 和时间范围定位一个或多个候选 TraceID。
4. TraceFinder 通过 Pfinder 获取候选 Trace 及调用拓扑。
5. TraceAnalyser 使用确定性逻辑完成筛选、裁剪和排序，识别错误、超时、高耗时或错误传播的关键 Span，并生成有序候选调查目标队列。
6. LogParser 对目标系统执行受限的只读日志查询，完成结构化、去重、上下文截取和脱敏。
7. GitWorkspaceManager 将目标版本克隆到隔离的临时只读工作区；如果无法确定线上版本，记录版本假设。
8. 主调查 Agent 通过 CodeAnalysisProvider 调用 Codex CodeInvestigator，结合关键 Span 和脱敏日志证据调查相关代码路径。
9. Verifier 调用 HypothesisVerifier，综合 Trace、日志和代码证据验证根因候选，并识别支持证据、冲突证据和证据缺口。
10. 证据不足时，主调查 Agent 根据补充调查请求继续查询日志或调用 CodeInvestigator；当前目标不是根因时，优先调查 Trace 队列中的其他候选，只有发现 Trace 外的新依赖时才创建 NextHop。达到终止条件时停止。
11. 系统输出诊断结果，并将完整调查过程保存到 InvestigationStore。

## 4. 验收通过标准

Demo 同时满足以下条件时，主验收场景通过：

- 能从不包含 TraceID 的问题输入中提取有效调查线索。
- 能通过业务 Key、起始系统和时间范围找到候选 TraceID；多候选时能够给出可解释的筛选依据。
- 能从 Pfinder 结果中识别至少一个需要优先调查的异常节点，并保留 TraceID、SpanID 或等价来源定位。
- 不将完整原始 Trace 和无关生产日志直接放入 LLM 上下文。
- GitWorkspaceManager 只克隆受信任的仓库，并能在调查结束后清理临时工作区；认证信息不会进入 URL、日志或模型输入。
- CodeInvestigator 能在指定仓库版本和调查预算内返回带 commit、文件路径和行号的代码证据，而不是只返回无来源的自然语言结论。
- HypothesisVerifier 能区分支持证据、冲突证据和缺失证据，并明确 RuntimeVerifier 是否执行。
- LLMProvider 返回格式错误、字段缺失或调用失败时，主流程能够显式记录并重试、降级或终止。
- UsageMonitor 能按调查任务和步骤统计调用次数、耗时、错误、重试以及供应商返回的 Token/成本信息；无法获取的指标明确标记为未知。
- UsageMonitor 不保存完整 Prompt、原始日志、代码内容或访问凭证。
- 只有临时错误会进行有限重试；确定性错误不会被无意义地重复调用。
- CodeInvestigator 超时或达到预算后能够保留部分证据，Pfinder 或日志无结果时能够按设计降级。
- 重试、结构化修复、降级和最终失败均写入 InvestigationStore 与 UsageMonitor。
- 主 Agent 只加载已配置的固定策略版本，运行期间不会自行修改代码、Prompt、工具或调查规则。
- 最终结果使用 `VERIFIED`、`SUPPORTED_HYPOTHESIS` 或 `UNRESOLVED` 之一，并说明终止原因和验证范围。
- 最终结论能够回溯到每一步查询、工具调用和证据来源。
- 调查遇到中断或可重试失败后，可以从 InvestigationStore 恢复，而不是重新开始全部步骤。
- LangGraph Checkpointer 与 InvestigationStore 职责分离但可以共用一个 SQLite 文件，重启恢复不会重复记录已完成步骤。
- SQLite 中不保存原始生产日志、完整代码、完整 Prompt 或访问凭证。
- CLI 能展示调查进度和 API 用量，并在结束时输出人类可读报告和结构化 JSON。
- 所有生产数据访问均为只读；Demo 依赖运行环境预先配置的权限，并遵守查询范围和脱敏要求。

## 5. 必须覆盖的异常路径

除主验收场景外，至少使用合成或匿名化数据验证以下行为：

- 用户输入缺少业务 Key、起始系统或有效时间范围。
- 根据日志无法找到 TraceID，系统降级为基于日志和代码的逐系统调查。
- 找到多个候选 Trace，无法唯一确定时保留候选及不确定性。
- Pfinder 调用链因采样、未埋点或异步调用而不完整。
- CodeInvestigator 或日志查询返回无结果、超时或格式错误。
- LLMProvider 返回不符合结构化约束的结果，修复重试后仍然失败。
- 外部 API 返回限流、临时服务错误或确定性参数错误。
- 调查出现循环调用、重复系统或超过最大深度。
- 达到时间或 Token/成本预算时输出当前最佳假设，而不是无限继续。
- RuntimeVerifier 未实现或未执行时，结果不会被错误标记为已完成运行时验证。

## 6. 第一版非目标

第一版 Demo 不包含：

- Case Memory 的存储和相似案例检索实现。
- RuntimeVerifier 的动态验证实现。
- 多个平级自治 Agent 的协作。
- Code Graph 建设。
- 流量回放和生产环境复现。
- 自动生产变更、自动修复或其他有副作用的操作。
- 通用企业级调用图或可观测性平台。
- 细粒度权限判断、权限申请和人工审批流程。
- 自动充值、账单管理或供应商配额修改。
- 分布式锁、数据库高可用和多实例并发执行。
- HTTP API、Web UI、用户会话和多租户能力。
- 专门的 RLM 框架或递归上下文执行引擎。
- 自动策略生成、在线自我修改、自动评测和自动发布。

## 7. 安全与数据要求

- 仓库内不得提交真实生产日志、客户数据、访问令牌、内部地址或连接信息。
- 测试夹具和演示截图使用合成数据或彻底匿名化的数据。
- 日志进入 LLM 或 CodeInvestigator 前必须完成裁剪和脱敏。
- 外部模型只接收完成当前调查所需的最小上下文。
- CodeInvestigator 不直接访问生产日志平台，只能使用主调查 Agent 提供的证据。
- Codex 默认只读，不执行仓库脚本，也不拉取 submodule 和 Git LFS 大文件。
- 任何权限不足、数据源不可用或验证未执行的情况都必须显式记录，不能静默猜测。
