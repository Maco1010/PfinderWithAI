# 根因定位
## 背景
  
* 对于企业级的系统，当出现某些线上问题时，经常由于链路过长，且链路中的研发负责人不同，导致排查问题时间过长。对此，本项目希望打造一个agent，为技术人员提供能力，可以在链路中跨系统定位问题。
* 难点：企业级系统大多是微服务架构，跨系统的调用有很多，跨系统定位问题十分困难

## 问题描述

* 通常出现一个线上问题后，一个简单的问题定位方式描述如下
1. 运营/产品 反馈线上问题，如trade0001 交易失败
2. 上游系统【A】查阅日志，发现系统【B】提供的交易接口返回失败，于是A系统负责人联系B系统负责人【带有日志信息】
3. 系统【B】查询自己系统逻辑以及日志信息：系统B发现自己的处理逻辑是先查询系统【C】做校验，之后在调用系统【D】做交易；而日志信息表明是系统【D】的接口超时，于是使用日志信息联系系统【D】负责人
4. 系统【D】负责人根据日志信息，查阅自己系统逻辑，发现是系统调用外部http接口超时，于是定位问题为外部http接口【非公司内部系统提供，如外部渠道】超时，并将问题逐层向上反馈。
* 综上所述，定位问题的链路通常会很长，而这个过程更像是搜索一颗树【or多颗】，然后再回溯的过程

## 概要设计

### 本期目标

* 本期实现简单调用链的问题定位，如系统 `A -> B -> C/D`。
* 第一版使用公司内部已有 API 获取真实的系统仓库定位信息和日志信息，并将目标版本的代码克隆到临时只读工作区供代码调查使用。
* 接入公司内部 Pfinder，通过调用链数据缩小调查范围，识别异常、超时或高耗时节点；Agent 再结合对应系统的日志和代码确认根因。
* Pfinder 作为调用链证据源，不承担完整的根因判断；日志用于确认运行时事实，代码用于解释系统行为，Agent 负责组织调查过程并关联证据。

### 数据源

* **代码仓库元数据 API**：获取目标系统的 Git 仓库地址和故障时对应的 commit、tag 或发布版本；代码内容通过 Git 克隆到临时工作区获取。
* **日志 API**：根据系统、时间范围、业务 Key、TraceID 等条件查询日志。
* **Pfinder API**：查询一次请求的跨系统调用链、Span 父子关系、耗时、状态和异常信息。具体 API 能力和返回结构待补充。

以上数据源通过独立适配器接入，避免核心调查逻辑直接依赖公司内部 API 的具体协议。

### 调查流程

1. **问题分析**：使用 LLM 从问题描述中提取现象（异常、错误、不匹配等）、业务 Key（订单号、ID 等）、起始系统和时间范围。缺少必要信息时，应明确列出待补充项。
2. **定位 Trace**：如果输入中包含 TraceID，直接查询 Pfinder；如果没有 TraceID，先使用起始系统、业务 Key 和时间范围查询日志，从日志中提取候选 TraceID。若仍无法找到 TraceID，则保留基于日志和代码逐系统调查的降级路径。
3. **分析调用链**：通过 Pfinder 获取完整或部分调用链，识别错误、超时、高耗时和状态异常的 Span，生成按优先级排列的候选调查目标。候选目标只是优先调查对象，不代表已经确认根因。调用链可能因采样、未埋点或异步调用而不完整，不能仅凭缺失 Span 判断某个系统未参与调用。
4. **构建调查查询**：结合问题、调用链和已有日志，为目标系统构建代码及日志查询。目标代码按照指定版本克隆到临时只读工作区，由代码调查 Agent 进行跨文件静态分析；Code Graph 作为候选增强方案，具体实现待验证。
5. **系统内根因分析**：关联目标 Span、运行日志和相关代码，区分已确认事实、推断和未知项，判断根因是否位于当前系统。
6. **跨系统继续调查**：如果当前目标不是根因，优先从 TraceAnalyser 生成的队列选择尚未调查的候选目标；只有日志或代码发现 Trace 之外的新系统、异步调用或外部依赖时，才创建 NextHop。继续调查时携带已有证据，并记录已访问系统及最大深度、时间或成本等终止条件。
7. **结构化输出**：返回根因或当前最佳假设、置信度、调查路径、证据链、未决问题和建议动作。结论必须能够追溯到 Pfinder、日志或代码中的具体证据。
8. **中间数据记录**：记录每一步的输入、查询、证据、判断和下一步，支持调查回放。随着问题数据积累，可以探索反向构建或补全跨系统调用关系，但不作为第一版本的必要目标。

### 调用链接入边界

* 第一版优先复用 Pfinder 已有能力，不重复建设分布式追踪平台。
* 核心系统定义统一的 `TraceProvider` 接口，Pfinder 作为首个实现，以便测试、替换或未来兼容 OpenTelemetry 等数据源。
* Pfinder 结果需要保留来源定位，例如 TraceID、SpanID 或可访问链接，作为诊断证据的一部分。
* 所有接入默认只读；真实日志、业务数据和模型输入需要遵守权限控制及脱敏要求。
  
## 技术选型

* 调用链数据优先通过公司内部 Pfinder API 获取，具体能力和接口契约待整理。
* 生产日志数据量较大，不能全部放入模型上下文。第一版先通过业务 Key、时间范围、系统和 TraceID 做渐进式检索与上下文裁剪。
* 第一版不引入专门的 RLM 框架，先使用渐进检索、裁剪、分段和摘要处理大规模上下文；是否引入 RLM 需要根据真实日志场景的用量和效果数据决定。
* 第一版通过 Git 将指定版本克隆到临时只读工作区，并使用 Codex SDK 进行代码调查；后续再评估 Code Graph 对跨文件调用关系和下一跳识别的提升。
* 第一版 Agent 流程编排使用 LangGraph，主流程通过统一的 `LLMProvider` 接入公司内部或外部模型，代码调查使用 Codex SDK；InvestigationStore 和 LangGraph Checkpointer 在单机 Demo 中使用职责分离的 SQLite 持久化，具体 LLM 模型和 Code Graph 方案仍待讨论。
* 第一版不实现细粒度权限控制和人工审批流，默认运行身份已完成必要授权且所有操作只读；通过统一的 UsageMonitor 记录模型和外部 API 的调用量、耗时、错误、重试及可获得的 Token/成本信息。
* 第一版只提供 CLI，运行时展示调查进度和 API 用量，最终输出可读报告与结构化 JSON；HTTP 接口和前端根据后续需要包装，不纳入当前范围。
* 外部调用只对超时、限流和临时服务错误进行有限重试；确定性错误不自动重试。Pfinder、日志或代码分析部分失败时保留已有证据并显式降级，所有重试和降级都写入调查轨迹与 UsageMonitor。
* 第一版不实现运行时自我改写；调查策略和 Prompt 的改进只能基于历史轨迹离线产生，经评测和人工审核后按版本发布。`InvestigationStrategyProvider` 第一期只提供固定默认策略。
